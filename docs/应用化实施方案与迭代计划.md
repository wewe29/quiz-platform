## 0. 一页结论

**做什么**：把「单科单页刷题网页」升级为**多学科刷题小应用**——一个带门户首页、多个学科子站、统一数据契约、统一构建门禁、可安装可离线的静态 Web 应用（PWA）。首批接入四门课：线性代数（已就绪）、高等数学（架构已就绪）、机器学习、数据可视化（内容已就绪）。

**技术路线（一句话）**：静态优先，**不引前端框架、不建后端**。复用高数项目已验证的模块化架构（core/ui 分层 + 按章分片 JSON）+ 线代项目已验证的内容门禁流水线（SymPy 复核、答案键自洽审计、口径单一事实源），外面套一个轻门户与 PWA 壳。云同步做成**触发式**（迭代 5），痛点真实存在才启动。

**交付边界（2026-10-31 修订）**：本项目的终点是**校验全绿的 `dist/` 静态产物**。托管（GitHub Pages / OSS / Vercel / 内网服务器 / 本机 `http.server`）由使用者按自己的方式部署，方案不预设、不依赖任何一家；平台仓里现存的 Pages workflow 只是「恰好可用的一种自动化」，删掉不影响任何功能（见 §9 交付说明）。

**迭代总览**（每轮都有一条「用户能自己走通」的路径，走不通就是没做完）：

| 轮次 | 主题 | 工作量 | 核心交付 |
|---|---|---|---|
| 0 ✅ | 基线固化 + 门禁 CI | 0.5 天 | 门禁自动化全绿，现状受保护 |
| 1 ✅ | 门户 + 线代子站化 | 3–4 天 | 门户上线，线代拆为 shell+数据分片，双输出保留 |
| 2 ✅ | 高数并入 + 统一 schema | 3–4 天 | 两学科并存（1356 题），模板盖章防分叉 |
| 3 | 应用化体验（PWA/导入导出/路由） | 3 天 | 可安装、断网可刷、进度可迁移 |
| 4 | ML + 数可视内容接入 | 1–2 周 | 四学科齐备，内容流水线通用化 |
| 5 | 云同步（触发式） | ~1 周 | 仅当多设备同步成为真实痛点时启动 |

### 2.2 边界（做什么 / 坚决不做什么）

**不做**（写下来防止范围蔓延）：
- ❌ 用户注册/登录体系（迭代 5 的匿名设备同步除外，且是可选项）
- ❌ 后端题库编辑器/管理后台（内容生产继续走「改源码 + 门禁 + 构建」，这条流水线已被证明能挡住真实事故）
- ❌ 评论、社交、排行
- ❌ 移动 App / 桌面打包（PWA 安装已覆盖需求）
- ❌ 引入 React/Vue 等框架（见 §4.1 决策 D1）

### 2.3 非功能约束（从现状继承，不许回退）

| 约束 | 指标 |
|---|---|
| 零外部依赖 | 运行时不发任何第三方网络请求；KaTeX 与字体自托管 |
| 离线可用 | PWA 安装后断网可刷已缓存章节；单文件版继续作为「极端环境」兜底 |
| 性能预算 | shell 传输体积 ≤ 300KB（gzip 后）；单章 JSON ≤ 200KB；首屏可交互 ≤ 2s（4G 中端机） |
| 隐私 | 作答数据默认只存本地；导出/同步均为用户主动行为 |
| 可维护 | 任何题量/口径数字只写在一处；门禁拦截优先于人工检查；文档随代码同仓 |

## 3. 统一数据契约（schema v2）

以**高数 v2 schema 为基线**（它已是线代 schema 的严格超集），做三点收敛：

1. **通用化**：`chapter` 上限从硬编码 12 改为随学科配置（`subject.chapters`）；知识点登记表从 schema.js 内置改为随学科 JSON 下发（`sections`）。
2. **学科标识**：顶层增加 `subject` 元数据块：

```json
{
  "subject": {
    "id": "linalg",
    "name": "线性代数",
    "textbook": "同济《工程数学·线性代数》第六版",
    "chapters": 6,
    "bankId": "linear-algebra-tj6-v1",
    "caliber": { "total": 500, "byType": {"single": 84, "...": 0}, "limits": {} }
  },
  "sections": { "1.1": "同济《线性代数》第六版 §1.1 二阶与三阶行列式" },
  "questions": [ … ]
}
```

3. **迁移**：线代现有字段 1:1 映射进新契约（无字段损失）；`build_convert.py` 做一次性转换并进 diff 门禁（转换前后语义字段全等）。**schema 单一事实源** = 平台仓 `shared/schema.json-schema` + 各学科构建期校验 + 运行期 quarantine 三层分工（沿用高数已有的分层：构建期穷尽拦截，运行期坏题隔离不崩站）。

## 4. 技术方案

### 4.1 架构：静态优先的 MPA+PWA

```
quiz-platform/                    ← 平台仓库（构建产物 dist/ 交付托管，方式由使用者决定）
├── index.html                    ← 门户（学科卡片 + 跨学科汇总）
├── assets/
│   ├── css/tokens.css            ← 全局设计令牌（深浅双主题）
│   ├── css/portal.css
│   ├── js/portal.js              ← 门户逻辑（读 registry.json 渲染）
│   ├── js/shared/                ← 跨学科共享模块（从高数 v2 提炼；迭代 2 落地）
│   │   ├── store.js              ← localStorage 命名空间 + 迁移器
│   │   ├── schema.js             ← 运行时校验 + quarantine
│   │   ├── judge.js / stats.js / sw-register.js
│   └── icons/                    ← PWA 图标（迭代 3）
├── subjects/
│   ├── registry.json             ← 学科注册表（id/名称/题量/入口/文案，构建时生成）
│   ├── linalg/
│   │   ├── index.html            ← 子站壳（复用学科壳模板）
│   │   ├── data/manifest.json    ← 数据契约（口径/文案/分片清单/SHA256）
│   │   ├── data/chNN[a-c].json   ← 按章分片（单分片 ≤200KB）
│   │   └── assets/js/            ← subject.js（配置）+ core/{store,bank}.js + app.js
│   ├── calculus/ …               ← 同构（迭代 2）
│   ├── ml/ …  └── dataviz/ …     ← 同构（迭代 4）
├── sw.js                         ← service worker（迭代 3；需 HTTPS 托管环境）
├── manifest.webmanifest          ← 迭代 3
└── tools/platform/               ← build_all.py（总构建）/ validate_platform.py / katex_assets.py
```

**运行时数据流**：子站壳加载 `subject.js` 配置 → `bank.js` 按当前筛选的章节懒加载 `data/chNN.json`（`fetch` + 内存缓存 + SW 落盘）→ 渲染层只挂当前窗口题卡（沿用线代 `visibleIds()` 窗口化——500 题实测结论，不许回退）。

### 4.2 决策记录（ADR）

| # | 决策 | 理由 | 放弃的选项 |
|---|---|---|---|
| D1 | **不引前端框架**，原生 ES Modules | 高数 v2 已验证该规模下原生模块够用；框架引入构建链与依赖审计成本，收益为零；StudyDesk 组件调研同结论「重资产才拼接」 | React/Vue/Svelte |
| D2 | **不建后端**（迭代 5 触发式除外） | 题库是静态内容；进度数据本地优先够用；后端带来运维/合规/可用性三种负担 | FastAPI+SQLite / Supabase（先行） |
| D3 | **统一 schema 以高数 v2 为基线** | 它已是线代 schema 超集且带 provenance（真题溯源结构化） | 反向（线代为基线）会让高数丢字段 |
| D4 | **平台单仓单产物**：一套 `dist/` 静态目录交付，**托管方式与本项目解耦** | 跨学科共享 tokens/schema/sw 需要同仓原子变更；dist 是纯静态相对路径结构，任何静态托管（Pages/OSS/Vercel/内网/本机）直接可用 | 每学科一仓；绑定特定托管平台 |
| D5 | **内容生产留在各学科目录**，平台仓只收构建产物 | 各学科目录是独立工作区（更新指南已警告多会话并行修改）；现有门禁与口径机制不动 | 把 qa_bank 全部搬进平台仓 |
| D6 | **双输出保留**（多文件站点 + 单文件兜底） | 单文件离线是现役卖点（`更新指南.md`「零外部依赖」条款）；高数 `build_static/build_single` 双脚本已是先例 | 只留多文件版 |
| D7 | **存储迁移走「新键 + legacy 备份」** | 线代 app.js 已有 `la_quiz_v1` → `la_quiz_v1-legacy-*` 机制，扩为按学科 `quiz-<subject>-v2` | 原键原地升级 |

### 4.3 内容流水线通用化

保持「**各学科目录 = 内容生产地**」（D5），平台只约定产物接口：

```
5-docs\线性代数复习资料\tools\          5-docs\高等数学复习资料\tools\
  qa_bank/ch*.py + target.py      →       build_subject.py（按学科参数化）
  update_site.py（8 道门禁）               ├─ 门禁（各科现有门禁全量跑）
  → 01《…》题库刷题网页.html（单文件）      ├─ data/chNN[a-c].json（分片导出 + manifest）
  → mcode 暂存（单文件版自有渠道）          └─ subjects/<id>/ → build_all 汇入 dist/
```

新增 `build_subject.py`（放各学科 tools，先在线代落地）：在现有 `update_site.py` 的 8 步之后追加「分片导出 + schema 校验（对照平台 schema.json-schema）+ 产物清单（manifest: 题量/SHA256/构建时间）」。**平台仓不信任任何未带 manifest 的产物**，门户渲染前校验。

ML/数可视（迭代 4）走同一条流水线：新增 `qa_bank_md` 解析器，把现有 md 小测结构化入库（题型以简答/计算为主，参照线代采分点体例），内容门禁按学科裁剪（ML 无数值题则跳过 SymPy，保留答案键↔解析自洽审计）。

### 4.4 产物交付与可选 CI（部署不在本项目范围内）

- **交付物**：`python tools/platform/build_all.py --dist` → `dist/` 目录（门户 + 全部学科子站 + 自托管 KaTeX），**100% 静态、相对路径、零第三方依赖**——把它放进任何能吐静态文件的地方就是完整网站（本机 `python -m http.server -d dist` 即可预览）。
- **部署由使用者自理**：不预设托管平台、不在验收标准里出现「线上验证」；各轮验收一律以「本地/任意静态服务器上走通演示脚本」为准。
- **可选的自动化**（已就位、可整体删除而不影响平台）：平台仓 `.github/workflows/deploy.yml` 在 push 时重建 dist 并发布到 GitHub Pages；单文件版仓 `linear-algebra-quiz` 的 `ci.yml` 跑门禁 + 漂移检查。它们只是「门禁自动化的现成载体」，不是交付链的必要环节。
- **一个客观技术约束**（托管方需知）：迭代 3 的 PWA（service worker / 安装）要求 **HTTPS** 托管环境（`http://localhost` 除外）；其余全部功能在纯 HTTP 静态托管下同样可用。

## 5. 工程纪律（移植 StudyDesk R1–R5，逐条落地）

| R1 每轮结束有一条用户可走通的路径 | 每轮验收标准第一节固定为「演示脚本」；用 browser-use 冒烟清单实测（本会话已验证该方法可行） |

## 9. 交付说明（给托管者）

**你收到的是什么**：`python tools/platform/build_all.py --dist` 生成的 `dist/` 目录——

```
dist/
├── index.html                 门户
├── assets/                    门户样式脚本 + 全局 tokens
└── subjects/
    ├── registry.json          学科注册表
    └── linalg/                线代子站（壳 + 8 个数据分片 + 自托管 KaTeX）
```

**托管要点**（全部来自构建产物的既定事实，无隐藏要求）：
1. **任意静态文件服务即可**：Nginx/Apache/OSS+CDN/Vercel/Netlify/GitHub Pages/`python -m http.server` 均可；无服务端逻辑、无构建时依赖、无跨域需求。
2. **路径无关**：全部引用为相对路径，部署在域名根、子路径（如 `/quiz/`）均可。
3. **HTTPS 才有 PWA**：迭代 3 之前不依赖 HTTPS；启用 PWA 后需要 HTTPS（或 localhost）。
4. **缓存建议**（可选优化）：`data/*.json` 与 `assets/vendor/` 可长缓存（内容变更时文件哈希随 manifest 变化）；`index.html` 与壳 HTML 建议短缓存或 no-cache。
5. **完整性校验**：发布前可跑 `python tools/platform/validate_platform.py`（在平台仓根），任何 manifest/SHA256/预算问题都会非零退出。
6. **平台仓里的 GitHub Actions workflow 是可选自动化**，不是交付链必需品；不需要自动部署可直接删除 `.github/` 目录。
